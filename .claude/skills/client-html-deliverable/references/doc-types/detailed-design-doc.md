# 文書タイプ: 詳細設計書（detailed-design-doc）

客先提出用の正式成果物。ソースは設計ナレッジ（コンポーネント図・データモデル・シーケンス図・状態遷移図・API仕様等、機能単位で整理された技術文書）。実際のファイル構成・命名はプロジェクトごとに異なるため、変換前に必ず実物を確認する——ファイル名を推測しない。これらのソースは吸収・削除せず、独立した技術文書として維持したまま、詳細設計書はそこから**生成**する（転記でなく参照）。

MD原稿の作成→HTML化の手順自体は`SKILL.md`の手順3〜11に従う（本ファイルは章立てのみを定義し、生成プロセスを再定義しない）。

## 基本設計書との関係

章構成は`basic-design-doc.md`の「基本設計書↔詳細設計書 全章対応表」と1:1で対応する。基本設計書の章がどこにも脱落しないことを保証するため、新しい章を追加する場合は必ず基本設計書側の対応表も更新すること。

原則：**基本設計書＝一覧・関連図・概要・方針止まり（WHAT）、詳細設計書＝フィールド単位・アルゴリズム・分岐条件・実装値（HOW）**。各章の具体的なWHAT/HOW境界は`basic-design-doc.md`の対応表を参照し、本ファイルでは複製しない。

## テスト文書との関係

単体・結合・総合テストの仕様・設計は本書に含めず、別文書（テスト仕様書／テスト設計仕様書）とする（ISO/IEC/IEEE 29119、国内実務テンプレートでも要件定義書・基本設計書・詳細設計書とテスト仕様書は並列の別文書として扱われるのが一般的）。本書側には、テスト容易性に必要な設計事項（例：モック可能なIF境界、リトライ/排他制御の観測可能性）と、対応するテスト仕様書へのリンクのみを記載する。

トレーサビリティは次の参照鎖で保つ：要件定義書の要件ID／基本設計書10章の品質シナリオID → 本書の該当章（設計要素） → テスト仕様書のテストケースID。各章末に「関連テストケース」欄を設けてもよい（該当時のみ記載、必須ではない）。

## IPO記述（画面・API・バッチ共通の記述パターン）

機能単位の詳細仕様は「入力（Input）・処理（Process）・出力（Output）」の3点セットで記述する（国内SIの詳細設計標準パターン）。処理欄にはアルゴリズム・分岐条件・エラー処理を書く。IPOだけで表現しにくい複雑な分岐・並行処理はアクティビティ図・シーケンス図で補う。

## 使う機能コンポーネント

- ほぼ確実に`references/components/multifile-packaging.md`が要る（機能単位で章が多くなる）
- シーケンス図・クラス図・アクティビティ図が要るなら`references/components/plantuml-embed.md`
- 画面詳細仕様（2章）でUIモックアップが要る場合はUIモックアップ4パターン（`SKILL.md`参照）を画面ごとに使う

## 客先公開範囲・TBDの扱い

- ソース側の社内向け注記（レビュー指摘の記録、AI作業記憶前提の書きぶり等）は生成時に転記しない
- 未確定事項（9章含む）は`callout ask`で明示し、「未解決」「設計フェーズで確定」等の表現に統一する（断定しない）
- 承認プロセス・契約上の扱い（客先が詳細設計まで正式承認するか、参考提示に留めるか、承認後の変更管理手順）はこのSkillの対象外。人間が別途判断する
