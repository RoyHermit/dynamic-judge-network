# 文書タイプ: 要件定義書（requirements-doc）

客先提出用の正式成果物。ソースはプロジェクトの要件一覧（スプレッドシート・CSV・Markdown等）とプロジェクト概要資料。要件一覧の実際の列構成はプロジェクトごとに異なるため、変換前に必ず実物を確認して列を把握する——列名を推測しない。ソース側は「AI作業用の整理資料」であり、そのまま客先に見せない。ファイル名・行番号も引用しない——「要件一覧の『（概要列のテキスト）』の項目」という形式で参照する。

識別子・内容・状態などに相当する情報がソースに存在するかを実物で確認し、存在する情報だけを客先向けの表現に対応付ける。**欠落している項目を推測・補完しない**。承認者・承認日・社内トラッキング用フラグのような社内管理専用の列を持つソースもあるが、これも決め打ちせず実際にどの列が該当するかをソースを見て判断する。

## 章立て（目安。プロジェクトの実情に合わせて増減してよい）

1. **目的・背景** — 何のためにこの要件定義書があるか、対象プロジェクトの概要
2. **用語定義** — プロジェクト固有語・略語の一覧
3. **業務要件** — 客先の業務課題・達成したいゴール（プロジェクト概要資料ベース）
4. **機能要件一覧** — 要件一覧にカテゴリ分類があればそれごとに章を分け、各要件を表にする。表の列は既定を決め打ちせず、確認済みのソース項目から客先向けに見せる項目を選ぶ。**承認者・承認日・社内トラッキング用フラグ・ファイル名・行番号のような社内管理専用の列はそのままの体裁で転記しない**——確認済みのソース項目だけを用いて客先向けに読める形（内容を示す文章、状態情報がソースにある場合のみ状態バッジ、といった具合）に整形する。ソースに無い項目を補って作らない
5. **非機能要件** — 性能・可用性・セキュリティ等（該当する要件がソースにあれば分類、無ければ設計資料等から補う）
6. **画面一覧** — 画面ごとに1セクション、UIイメージは`SKILL.md`の4パターン（mock-panel/mock-modal/mock-tabbar/mock-chat）から選ぶ
7. **スコープ外** — 今回対象外とした項目とその理由
8. **前提条件・制約**
9. **改訂履歴** — `template.html`の`doc-manifest`に記載（章として重複させない）

## 本文パターン

- 要件一覧はtableコンポーネントを使う。1行1論点、詳細列が長文になる場合も「1セル=1`<p>`」ではなく、詳細列内で論点ごとに`<p>`を分けるか箇条書きにする
- 客先からの明示的な要望ではなく、こちら（ベンダー）側の提案・判断である旨が必要な箇所は「追加提案」という語を使う（「追加要望」は使わない。客先発案と自社発案を混同すると後工程の合意形成で揉める）
- 未確定・客先確認待ちの項目は`callout ask`で明示する

## 使う機能コンポーネント

- 要件数が多く1ファイルでは長すぎる場合（章ごとに分けたい場合）は`references/components/multifile-packaging.md`
- 業務フロー図が必要な場合は`diagram > flow-steps`（PlantUMLほど複雑でなければこちらで十分）

## トレーサビリティ

要件定義書の各要件と、基本設計書の対応箇所（画面・コンポーネント）を後から突き合わせられるよう、要件見出しに安定したアンカーID（`id="req-<連番>"`等）を振っておく。複数ファイル分割時は`multifile-packaging.md`のリンク規約に従う。
