# 文書タイプ: 基本設計書（basic-design-doc）

客先提出用の正式成果物。ソースはアーキテクチャ概要・技術スタック・セキュリティ設計等の資料と、プロジェクトが記録している設計判断記録（ADRなど）。これらのソースは吸収・削除せず、独立した技術文書として維持したまま、基本設計書はそこから**生成**する（転記でなく参照）。設計判断記録は全文を複製せず、要約＋リンクに留める。

MD原稿の作成→HTML化の手順自体は`SKILL.md`の手順3〜11に従う（本ファイルは章立てのみを定義し、生成プロセスを再定義しない）。

## 章立て：arc42（公式12章）＋国内SI標準の名称付きサブセクション

arc42は[公式12章構成](https://arc42.org/overview/)を採用する（品質要求とリスクを1章に統合しない）。**全章を必須にしない**——プロジェクトの規模・性質に対して過剰な章は「該当なし（理由: ○○のため省略）」の1行で済ませてよい。

第5章（ビルディングブロック）のみ、国内SIで一般的な成果物名（実務ブログ・テンプレート記事に基づく。IPA一次資料での厳密な確認はしていない）に沿ったサブセクションへ再構成している。客先が見慣れた語彙（画面設計・DB設計等）で書けるようにするため。

| 章 | 内容 | 主なソース |
|---|---|---|
| 1. はじめに・目標 | 本書の目的、読者、**優先順位付きの品質目標**（少数・要約レベル、各目標にID） | プロジェクト概要資料 |
| 2. 制約条件 | 技術的・組織的制約 | 技術スタック資料 |
| 3. コンテキスト境界 | システムと外部の関係（C4: System Context） | アーキテクチャ概要資料 |
| 4. ソリューション戦略 | 主要な技術判断の**物語的要約**（なぜその方式を選んだか、トレードオフ） | 設計判断記録（要約＋リンク） |
| 5. ビルディングブロック | 下記サブセクション参照 | 下記参照 |
| 6. ランタイムビュー | **代表的フローのみ**のシーケンス図（機能横断の代表パターンに限定、全分岐は書かない） | アーキテクチャ概要資料（`flow-steps`または複雑なら`plantuml-embed.md`） |
| 7. デプロイメントビュー | インフラ構成 | 技術スタック資料、関連する設計判断記録 |
| 8. 横断的関心事 | 認証・ロギング・エラー処理等の**方針レベル**（例:「JWTトークンで認証する」、実装値は書かない） | セキュリティ設計資料 |
| 9. アーキテクチャ判断 | 主要な設計判断の**索引表のみ**（タイトル・ステータス・1行要約。詳細は4章に委ね複製しない） | 設計判断記録一式 |
| 10. 品質要求 | **測定可能な**品質シナリオ（刺激・環境・応答・測定値。1章の品質目標IDと対応付け）。要件定義書NFR章との差分のみ | 要件定義書の非機能要件章 |
| 11. リスク・技術的負債 | 既知のリスク・技術的負債 | 設計時の判断記録 |
| 12. 用語集 | プロジェクト固有語 | 要件定義書の用語定義章と共通化してよい（複数ファイル分割時はリンクで参照） |

該当章が無い場合の書き方: 見出しの下に `<p class="frame-title">[理由]のため本章は対象外</p>` のように1行で明記し、空欄のまま残さない。

## 基本設計書↔詳細設計書 全章対応表（書き分け基準）

原則：**基本設計書＝一覧・関連図・概要・方針止まり（WHAT）、詳細設計書＝フィールド単位・アルゴリズム・分岐条件・実装値（HOW）**。詳細設計書のdoc-type（`detailed-design-doc.md`）はこの対応表と1:1で章を構成する。

| 基本設計書の章 | 対応する詳細設計書の章 | 対応なしの理由／書き分け基準 |
|---|---|---|
| 1 はじめに・目標 | 対応なし（詳細設計書0章が基本設計書との関係を記述） | 品質目標の要約はプロジェクト全体で1つ、機能単位に分解しない |
| 2 制約条件 | 対応なし | 制約は所与の前提。詳細設計は前提を実装するだけ |
| 3 コンテキスト境界 | 対応なし | システム境界はアーキテクチャレベルで完結 |
| 4 ソリューション戦略 | 対応なし | 「なぜその方式か」は基本設計書のみが持つ。詳細設計書は複製しない |
| 5-1 システム方式設計 | 詳細設計1章 全体構成 | WHAT=構成図・ミドルウェア一覧／HOW=個別コンポーネントの内部モジュール構造 |
| 5-2 画面設計 | 詳細設計2章 画面詳細仕様 | WHAT=画面一覧・遷移図・ラフレイアウト・項目一覧・アクション要約／HOW=画面イベント詳細（バリデーション・エラー文言・分岐条件） |
| 5-3 帳票設計 | 詳細設計3章 帳票詳細仕様 | WHAT=帳票一覧・出力項目概要／HOW=帳票編集の実装ロジック（書式・改ページ・集計） |
| 5-4 バッチ設計 | 詳細設計4章 バッチ詳細仕様 | WHAT=処理一覧・大まかなフロー／HOW=各ステップのアルゴリズム・リトライ/排他制御 |
| 5-5 データモデル・永続化設計 | 詳細設計5章 データモデル・永続化詳細 | WHAT=論理データモデル（ER図/グラフモデル/ベクトルインデックス構成等）・論理項目定義・CRUD図またはアクセスパターン一覧／HOW=物理データ構造・属性型・識別子・関係・制約・索引/検索方式・分割/保持/整合性・移行方式（データストア種別ごとの実装詳細）、ファイルフォーマット詳細 |
| 5-6 外部インターフェース設計 | 詳細設計6章 外部インターフェース詳細仕様 | WHAT=関連図・IF一覧・概要／HOW=フィールド単位のリクエスト/レスポンス・エラーコード一覧 |
| 6 ランタイムビュー | 詳細設計7章 ランタイム詳細 | WHAT=代表フローのみ／HOW=全フロー・全分岐、メソッド/クラス粒度、タイムアウト・リトライ実装値 |
| 7 デプロイメントビュー | 対応なし | 物理配置は技術スタック資料・関連する設計判断記録が正本のまま、機能単位に分解しない |
| 8 横断的関心事 | 詳細設計8章 横断的処理詳細 | WHAT=方針レベル／HOW=トークンライフサイクル・ログフォーマット・エラーコード体系の実装詳細 |
| 9 アーキテクチャ判断 | 対応なし | 設計判断記録そのものが正本。複製しない |
| 10 品質要求 | 対応なし（機能単位で測定方法の注記が要る場合のみ対応する詳細設計章に脚注） | 品質シナリオは基本設計レベルで完結 |
| 11 リスク・技術的負債 | 対応なし | 設計判断レベルのリスクであり実装詳細に分解しない |
| 12 用語集 | 詳細設計書10章 用語集 | 共通化。詳細設計書側は基本設計書へのリンクのみでも可 |

## C4モデルによる段階的ズーム（5-1向け）

システム構成図は3階層まで用意できる（過剰なら3を省略しコンテキスト+コンテナ図のみでよい）。

1. **System Context**：客先システム・利用者・本システムの関係のみ（技術要素を書かない）
2. **Container**：フロントエンド/バックエンド/DB/外部API等の主要コンテナ間の関係
3. **Component**（必要な場合のみ）：複雑性が高い、セキュリティ境界がある、独立デプロイされる、または重要なランタイムを持つコンテナのみ内部を展開する。全コンテナに対して機械的に作らない

図はPlantUMLで事前レンダリングする（`references/components/plantuml-embed.md`参照）。C4記法が要らない単純な構成図はインラインSVGで十分。

## 使う機能コンポーネント

- ほぼ確実に`references/components/multifile-packaging.md`が要る（章数が多くなりやすい）
- 構成図・シーケンス図・クラス図が要るなら`references/components/plantuml-embed.md`
- 画面設計（5-2）を含める場合はUIモックアップ4パターン（`SKILL.md`参照）を画面ごとに使う

## 客先公開範囲・TBDの扱い

- ソース側の社内向け注記（レビュー指摘の記録等）は生成時に転記しない
- 未確定事項は`callout ask`で明示し、「未解決」「設計フェーズで確定」等の表現に統一する（断定しない）
